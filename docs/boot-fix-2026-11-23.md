# Boot fix — installed Fedora 45 (2026-11-23)

## Symptom

The installed Fedora 45 system on `/dev/nvme0n1p7` could not be used without
the Live USB: the kernel booted, but no GNOME login screen appeared. The user
therefore booted the SanDisk USB stick (`BootCurrent: 0007`) for all work.

## Evidence from the installed system's journal

Journal: `/var/log/journal/c86b9190d4074f36aba2b52a689d2b84` in the installed
root (read from the Live USB at
`/run/media/liveuser/fedora/root/var/log/journal/...`).

- Boot `9e83e5f06da7421fa33716c1740815d2` (2026-11-23 00:51 UTC) reached the
  desktop stage and later shut down cleanly, so **disk boot itself was not
  broken**: root, `/boot` and `/boot/efi` all mounted and `systemd` finished.
- `mtgpu` loaded at 00:51:53 despite the project's blacklist:
  `mtgpu: loading out-of-tree module taints kernel.`,
  `Matched GPU device id is: 0x0102`,
  `[drm] Initialized mtgpu 2.0.0 for 0000:01:00.0 on minor 0`.
- GNOME Shell then crashed repeatedly in its KMS thread:
  `gnome-shell[3203]: segfault ... in libmutter-cogl-51.so...`,
  `mtgpu mtgpu.4.auto: comm = gnome-shell, pid = 3203, force destroy app memory context`,
  `org.gnome.Shell@gdm.service: Failed with result 'core-dump'`, and finally
  `GdmLocalDisplayFactory: maximum number of display failures reached. Giving
  up.`
- Earlier boots on 2026-11-23 show the same pattern, with
  `libsrv_um_MUSA.so` threads in the `gnome-shell` coredump. The MUSA Mesa DRI
  drivers (`/usr/lib64/dri/musa_dri.so`, `kms_swrast_musa_dri.so`) are loaded
  by Mesa when an `mtgpu` DRM card is present.

## Root cause

`/etc/modprobe.d/blacklist-mtgpu.conf.bak` had been renamed away, so the
**active** modprobe configuration contained only
`90-mtgpu-headless.conf` (driver options, no blacklist). The initramfs still
contained the blacklist, but after switch-root udev matched PCI device
`1ed5:0102` and auto-loaded `mtgpu`. The resulting DRM card was picked up by
Mesa/GNOME Shell, which loaded the MUSA Mesa user-space and segfaulted in the
KMS thread. GDM gave up after repeated failures, leaving no login screen.

This is the same failure mode described in the project's archived notes; the
blacklist is the intended, validated host state. It prevents display-driver
collision and keeps the S30 unbound for compute-only use.

## Fix applied (2026-11-23 01:50 UTC)

All changes were made from the Live USB against the installed root with
`pkexec`; no package was reinstalled and no kernel module was loaded/unloaded.

1. Backed up every touched file to
   `/var/backups/musa-fedora-bootfix-20261123T015011Z` in the installed root
   (includes `efibootmgr-before.txt`, both modprobe configs, `grubenv`, and the
   stale boot entry).
2. Restored `/etc/modprobe.d/blacklist-mtgpu.conf` from the `.bak` file:
   `blacklist mtgpu`.
3. Retired the stale BLS entry `mtt-s30-test.conf` →
   `mtt-s30-test.conf.disabled` (it referenced nonexistent kernel
   `vmlinuz-7.2.13-200.fc44.x86_64`).
4. Changed EFI boot order from `0007,0004,...` to
   `0004,0005,0006,0000,0001,0002,0003,0007`: installed Fedora first,
   Windows/NVMe/firmware entries next, USB last as fallback. No boot option
   was deleted.

## Verification performed

- Active blacklist file contains `blacklist mtgpu`.
- `lsinitrd initramfs-7.3.4-300.fc45.x86_64.img` confirms the initramfs also
  carries `etc/modprobe.d/blacklist-mtgpu.conf`; no dracut config force-loads
  `mtgpu`.
- GRUB saved entry is `...-7.3.4-300.fc45.x86_64`, and the matching
  `vmlinuz`, `initramfs`, `System.map` and `config` files exist on `/boot`
  (`nvme0n1p5`).
- `efibootmgr` shows `BootOrder: 0004,0005,0006,0000,0001,0002,0003,0007`.
- Remaining valid BLS entries: 0-rescue, 7.2.15, 7.3.3 and 7.3.4 kernels.

**Not yet verified:** an actual reboot into the installed system from disk.
That requires removing the USB stick and rebooting; this Live USB session
cannot perform that reboot on the user's behalf. The user should remove the
USB pendrive and power on; if the GRUB menu appears, choose
`Fedora Linux (7.3.4-300.fc45.x86_64) 45 (Workstation Edition)`.

## Expected result and limits

- Expected: GNOME reaches the login screen on the Intel i915 display; `mtgpu`
  is not loaded and S30 remains unbound (`0000:01:00.0` has no driver).
- This does **not** enable MUSA GPU compute. Loading `mtgpu` remains gated by
  the unapproved `docs/maintenance-plan-mtgpu-load-2026-11-20.md`.
- If the login screen still fails, capture `journalctl -b -p warning` from the
  installed system and attach it; the backup directory above allows instant
  rollback of every change.

## Rollback

From any root shell on the installed system:

```sh
cp /var/backups/musa-fedora-bootfix-20261123T015011Z/blacklist-mtgpu.conf.bak \
   /etc/modprobe.d/blacklist-mtgpu.conf
rm -f /etc/modprobe.d/blacklist-mtgpu.conf
cp /var/backups/musa-fedora-bootfix-20261123T015011Z/mtt-s30-test.conf \
   /boot/loader/entries/mtt-s30-test.conf
efibootmgr -o 0007,0004,0005,0006,0000,0001,0002,0003
```

Rollback is not recommended: it restores the exact configuration that caused
the GDM crash.
