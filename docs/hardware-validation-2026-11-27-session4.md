## What was built

* `packaging/cuda-compat/bin/musify-text` — CUDA↔MUSA source porting tool
  (stdlib Python). Rule basis was derived, not copied: 4,020 name pairs in
  the generated compat maps were checked, and all but two
  (`cuuint32_t/cuuint64_t`) follow literal `cuda→musa` / `CUDA→MUSA` /
  word-start `cu(?=[A-Z])→mu` / `CU(?=[A-Za-z_])→MU` rewrites, so the tool
  ships exactly those family rules plus the full explicit map. It reports
  residual CUDA-only tokens (`--strict` fails on them) and rewritten names
  the 1.5.4 runtime does not export. Attribution: design intent follows
  Moore Threads' `tutorial_on_musa/musify` and `torch_musa`
  (BSD-3-Clause) helpers; implementation and rule derivation are this
  project's (MIT).
* `packaging/cuda-compat/cmake/{FindMUSA,MUSAConfig,MUSAConfigVersion}.cmake`
  — `find_package(MUSA)` in module and config mode; variable names follow
  the MT port convention (`MUSA_TOOLKIT_ROOT_DIR`, `MUSA_MCC_EXECUTABLE`,
  `MUSA_ARCH`, `musa_add_executable`) with the S30-correct defaults:
  SDK `/usr/local/musa-5.2`, runtime `/usr/local/musa`, arch `mp_10`.
* `gen-cuda-compat.py` now also generates `include/musa_rt154_names.h`:
  the post-vendor-header `extern "C"` undo of the nine versioned renames
  (e.g. `musaGetDeviceProperties→_v2`). Determinism re-proven: the four
  pre-existing generated files regenerated byte-identical.

## Root causes found while testing

1. **`musaGetDeviceProperties_v2` undefined link error** for musified
   sources: the 5.2.0 header renames the entry point to a `_v2` symbol the
   1.5.4 runtime never shipped. The CUDA path was already protected (the
   compat maps restore the base name); MUSA-named callers had nothing.
   Fixed by generating `musa_rt154_names.h` from the same export-derived
   data and force-including it from `musa_add_executable`.
2. **`extern "C"` omission in the generated pin** — first container run
   failed with a *mangled* undefined symbol. Fixed in the generator; the
   rebuild re-verified both suites.
3. **Wrong-runtime linkage via CMake** — `-L"${VAR}/lib"` inside
   `add_custom_command VERBATIM` produced an argument with embedded quotes,
   so `-L` was dropped and `ld` picked the SDK's `libmusart.so.5` (the ABI
   that segfaults against the 3.1.0 driver). Fixed with pre-built `-L…`
   argument variables; every gate now asserts
   `NEEDED libmusart.so.1.5` on the produced binary.
4. **Signing key drift** — the 2026-11-17 key turned out to be
   passphrase-protected despite documentation; headless `rpmsign` timed out
   in `pinentry-gnome3`. Rotated to
   `BFAB85E6884C116DAA985DF0C2B44B18E3841DC2` with a batch loopback recipe
   now baked into `scripts/rpm-signing.sh keygen`
   (see [rpm-signing.md](rpm-signing.md)).
